# Threat model (v0.2.0)

This tool is a local, narrow `Bash` PreToolUse policy. It is neither a transport integrity mechanism nor a shell sandbox. The protected assets are local credentials, user files, Claude Code settings, and the user's authority over tool execution. The trusted local base is the user's Claude Code installation, settings, hook files, Python/Bash runtime, and OS permissions. The API relay, repository files, web pages, tool results, and model output are outside that base.

| Attacker or failure source | Capabilities | What this project can do | What it cannot guarantee |
| --- | --- | --- | --- |
| API relay | Read and replace complete API requests and responses, including system text and user-looking messages | A local Bash hook can reject a matching proposed Bash command before execution, if installed and invoked | Verify message origin, keep the prompt contract intact, protect data already included in the request, or prevent all tool use |
| Third-party repository, page, or file | Plant instructions in content Claude reads, including `CLAUDE.md` | The prompt contract reminds the model to treat content cautiously; Bash gate catches a subset of resulting commands | Reliable prompt-injection blocking or trustworthy project instructions without user review |
| Polluted tool result | Add instructions to tool output | Same limited prompt reminder and downstream Bash gate | Decide whether model behavior complied without real-model experiments |
| Model misunderstands authorization | Propose an unsafe command despite the user's intent | Reject listed command shapes | Infer real user intent or adjudicate all legitimate destructive actions |
| Local ordinary malicious process | Edit files it can access as the same user, alter environment, or race local state | File permissions reduce accidental disclosure; the gate avoids logging command text | Defend against a same-user process able to edit settings, hook files, binaries, or launch modes |
| Full device compromise | Replace runtime, client, configuration, or OS | No meaningful protection | Local integrity, confidentiality, or availability |

The user may intentionally choose `bare`, `raw`, or `ccguard disable`. Those modes turn off this project's gate for their process or globally. `guarded` uses the gate only when the installed `PreToolUse` entry actually loads. Claude Code's own permission rules remain relevant; the gate gives no `allow` decisions.

The gate sees the literal `tool_input.command` before a `Bash` tool call. It does not observe the shell's later variable expansion, script contents, subprocesses, aliases, compiled tools, network requests made by other tools, or `Write`/`Edit`/MCP actions. A regular expression match is evidence of one command shape, not proof of full behavior. For broader restrictions, use Claude Code's [permission deny rules and tool controls](https://code.claude.com/docs/en/permissions), filesystem isolation, and network egress controls. `PreToolUse` can match other tool names, including MCP tools, but their input schemas and policies need separate design and tests; this project does not silently claim coverage.

Hook failure behavior depends on Claude Code. The current [Hooks reference](https://code.claude.com/docs/en/hooks) states that `PreToolUse` receives JSON on stdin; `hookSpecificOutput.permissionDecision: "deny"` rejects a call. Exit code 2 blocks and sends stderr as the reason. Ordinary nonzero exit and command-hook timeout otherwise continue through normal permissions. `onFailure: "block"` covers launch failure, invalid output, crash, and timeout starting in **Claude Code v2.1.295**. A synthetic local-API test verified allow, deny, missing-Hook, and timeout paths with real Claude Code v2.1.299 on Linux; older-version behavior and real-model behavior were not experimentally verified. On older clients, do not rely on timeout or failed-to-start behavior for fail-closed protection.
